# 手动发布导航任务流程

本文档用于人工启动智能工厂仿真，并验证任务服务器通过独立 Navigate Action
Server 连续执行当前导航路线。

相关文件：

- 完整系统入口：`src/smart_factory_bringup/launch/full_competition.launch`
- 任务节点组件入口：`src/smart_factory_mission/launch/mission.launch`
- 导航组件入口：`src/smart_factory_navigation/launch/navigation.launch`
- 导航运行参数：`src/smart_factory_navigation/config/navigation.yaml`
- 拟合路径：`src/smart_factory_navigation/config/pickup_staging_fitted_path.yaml`
- 任务测试客户端：`src/smart_factory_tests/scripts/send_navigation_task.py`
- 当前路线配置：`src/smart_factory_mission/config/pickup_staging_dev.yaml`
- 原始导航点记录：`docs/navi_pos.md`

## 1. 验证方式

| 验证方式 | 目标 | 是否经过任务服务器 | 是否经过 Navigate Action | 是否执行完整路线 |
|---|---|---:|---:|---:|
| 手动触发任务客户端 | 验证完整任务状态机和连续导航 | 是 | 是 | 是 |
| RViz `2D Nav Goal` | 验证单个位置是否可以到达 | 否 | 否 | 否 |

建议首先执行完整路线任务；如果某个点失败，再使用 RViz 单独验证该点。

## 2. 启动完整仿真

打开终端 1：

```bash
cd /home/ianichinose/gazebo_ws
source /opt/ros/noetic/setup.bash
source devel/setup.bash
roslaunch smart_factory_bringup full_competition.launch
```

`full_competition.launch` 默认启动以下组件：

| 组件 | ROS 节点 | 作用 |
|---|---|---|
| Gazebo Server | `/gazebo` | 运行物理仿真 |
| Gazebo GUI | `/gazebo_gui` | 显示仿真界面 |
| RViz | `/rviz` | 显示地图、机器人、路径和代价地图 |
| 地图服务器 | `/map_server` | 发布静态地图 |
| AMCL | `/amcl` | 机器人定位 |
| 导航服务器 | `/move_base` | 全局规划和 DWA 局部规划 |
| 导航 Action Server | `/smart_factory_navigation` | 定位检查、路线执行、路径跟踪和底盘对齐 |
| 感知服务 | `/cube_locator` | OCR 与 RGB-D 物块定位 |
| 任务服务器 | `/smart_factory_mission` | 编排总任务状态机并调用导航、感知和抓取子系统 |

主要启动参数：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `start_navigation` | `true` | 是否包含完整导航启动链 |
| `start_gazebo` | `true` | 是否启动 Gazebo |
| `gazebo_gui` | `true` | 是否显示 Gazebo GUI |
| `start_rviz` | `true` | 是否启动 RViz |
| `map_file` | `math_newest.yaml` | 导航使用的地图 |
| `global_inflation_radius` | `0.10` | 全局代价地图膨胀半径 |
| `local_inflation_radius` | `0.15` | 局部代价地图膨胀半径 |

图形渲染环境：

| 环境变量 | 值 | 作用 |
|---|---|---|
| `GALLIUM_DRIVER` | `d3d12` | 使用 Mesa D3D12 驱动 |
| `MESA_D3D12_DEFAULT_ADAPTER_NAME` | `NVIDIA` | 选择 NVIDIA 显卡 |
| `LIBGL_ALWAYS_SOFTWARE` | `0` | 禁止强制软件渲染 |

等待系统达到以下状态后再发送任务：

| 检查对象 | 正常表现 |
|---|---|
| Gazebo | 地图、机器人和物体完成生成 |
| RViz | 地图、机器人模型和激光数据正常显示 |
| AMCL | 日志出现 `odom received` |
| `move_base` | 全局和局部 costmap 初始化完成 |
| 导航 Action Server | 日志出现 `smart factory navigation ready on /smart_factory/navigation` |
| 任务服务器 | 日志出现 `smart factory mission ready on /sim_task/execute` |

统一入口会保证每个组件只启动一次。`mission.launch` 本身现在只启动任务节点，
用于组件级调试。

## 3. 手动发布连续导航任务

打开终端 2：

```bash
cd /home/ianichinose/gazebo_ws
source /opt/ros/noetic/setup.bash
source devel/setup.bash

rosrun smart_factory_tests send_navigation_task.py \
  --task-id manual_nav_001 \
  --target-class electronics \
  _server_wait_timeout:=1000.0
```

任务客户端参数：

| 参数 | 示例值 | 说明 |
|---|---|---|
| `--task-id` | `manual_nav_001` | 任务唯一编号，每次重新测试应更换 |
| `--target-class` | `food` | 目标类别 |
| `_server_wait_timeout` | `1000.0` | 等待任务 action server 的最长 ROS 时间 |

可用目标类别：

| 命令行值 | Action 常量 | 数值 |
|---|---|---:|
| `food` | `FOOD` | 0 |
| `daily` | `DAILY` | 1 |
| `electronics` | `ELECTRONICS` | 2 |

任务服务器会缓存已经完成的任务编号。重复使用同一个 `task-id` 时，可能直接返回之前的结果。因此重复测试时应使用递增编号：

```bash
--task-id manual_nav_002
--task-id manual_nav_003
```

## 4. 观察任务执行过程

任务阶段：

| 数值 | 状态名称 | 含义 |
|---:|---|---|
| 0 | `IDLE` | 等待任务 |
| 1 | `ACCEPT_TASK` | 接收任务 |
| 2 | `VALIDATE_TASK` | 校验任务字段 |
| 3 | `CHECK_LOCALIZATION` | 检查 AMCL 和 TF |
| 4 | `GET_PICKUP_STAGING_GOAL` | 加载当前路线 |
| 5 | `NAVIGATE_TO_PICKUP_STAGING` | 按顺序执行导航点 |
| 6 | `ARRIVED_PICKUP_STAGING` | 已到达最终暂存点 |
| 250 | `TASK_FAILED` | 任务失败 |

正常导航日志应按顺序出现：

```text
navigating to waypoint 1/34
waypoint 1/34 goal reached
navigating to waypoint 2/34
waypoint 2/34 goal reached
...
waypoint 34/34 goal reached
success=True stage=6 error_code=0
```

结果判定：

| 日志或结果 | 判断 |
|---|---|
| `waypoint N/34 goal reached` | 第 N 个点成功，任务将进入下一点 |
| DWA 短暂报警后机器人继续移动 | 规划器正在重试，不直接判定任务失败 |
| `retry=1` 后继续导航 | Navigate Action Server 的路线重试流程正常，Mission 已转发反馈 |
| `success=True stage=6 error_code=0` | 当前 34 点路线全部完成 |
| `TASK_FAILED` | 任务校验、定位或导航重试最终失败 |
| 长时间无 `/cmd_vel` 输出 | 需要检查定位、局部代价地图或 `move_base` 状态 |

## 5. 使用 RViz 手动验证单个导航点

如果需要单独测试某个位置：

1. 在 RViz 顶部选择 `2D Nav Goal`。
2. 在地图目标位置按下鼠标。
3. 拖动鼠标设置机器人到达后的朝向。
4. 松开鼠标发送目标。
5. 等待终端输出 `Goal reached`。

RViz 发布的目标会直接交给 `move_base`，不会调用 `/sim_task/execute`，因此这种方式只验证单点可达性。

需要严格验证 YAML 中的某个点时，从以下文件读取坐标：

```text
src/smart_factory_mission/config/pickup_staging_dev.yaml
```

## 7. 已经启动导航栈时的操作

如果另一个终端已经运行 `gazebo_nav.launch`，仍需启动 Navigate Action Server；
推荐让统一入口复用现有 `move_base`，并继续编排导航、感知和任务组件：

```bash
cd /home/ianichinose/gazebo_ws
source /opt/ros/noetic/setup.bash
source devel/setup.bash
roslaunch smart_factory_bringup full_competition.launch \
  start_navigation:=false \
  start_gazebo:=false \
  start_rviz:=false
```

组件级调试时，也可以先运行
`roslaunch smart_factory_navigation navigation.launch`，再在另一个终端运行
`roslaunch smart_factory_mission mission.launch`。完整抓取流程还需要感知服务。

## 8. 常见问题

| 现象 | 可能原因 | 处理方法 |
|---|---|---|
| 测试客户端提示 `action server is unavailable` | Mission 尚未完成启动 | 等待 Mission ready 日志，保留 `_server_wait_timeout:=1000.0` |
| Mission 提示 `navigation action server is unavailable` | Navigate Action Server 未启动或名称不一致 | 检查 `/smart_factory/navigation/status`，并确认已启动 `navigation.launch` |
| 出现同名节点被关闭 | 同时启动了多个底层仿真或导航入口 | 只保留 `full_competition.launch`，或复用导航时设置 `start_navigation:=false` |
| 机器人不移动 | 定位、TF、costmap 或 DWA 尚未就绪 | 检查 `/amcl_pose`、`/tf`、`/cmd_vel` 和两个 costmap |
| 某一点反复规划 | 局部轨迹暂时不可行 | 等待 DWA 重试；只有最终 ABORTED 才判定失败 |
| 重复任务立即返回 | 使用了已完成的 `task-id` | 换用新的任务编号 |
| RViz 单点成功但连续任务失败 | 单点可达，但任务状态或某个中间点异常 | 查看 `/sim_task/execute/feedback` 确定失败阶段 |

## 9. 停止系统

在启动 `full_competition.launch` 的终端按 `Ctrl+C`。正常关闭时会依次停止
任务、感知、RViz、AMCL、`move_base`、Gazebo GUI 和 Gazebo Server。
