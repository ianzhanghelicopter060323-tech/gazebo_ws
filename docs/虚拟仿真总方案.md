# 讯飞智慧工厂 Gazebo 虚拟仿真总方案

本文档用于指导 `Gazebo/` 文件夹内虚拟仿真部分的学习、运行、调试和比赛方案设计。当前版本先搭出总路线，后续再逐步补充实测截图、关键坐标、机械臂姿态参数和自动化脚本。

## 1. 资料来源与当前结论

已阅读/核对的本地资料：

- `rules/完整规则.pdf`：第二十一届全国大学生智能车竞赛，讯飞组赛项为“智慧工厂”。
- `docs/官方澄清_2026-06-05.md`：联网、大模型、红绿灯、识别板、仿真文件发布时间等澄清。
- `Gazebo/gazebo仿真操作手册.pdf`：官方 Gazebo 环境启动、建图、导航、抓取、释放、摄像头测试说明。
- `Gazebo/gazebo_ws/`：官方发布的 ROS/Gazebo 仿真工作空间。
- `Gazebo/仿真演示视频.mp4`：后续用于复核完整操作流程和机械臂姿态。

关键结论：

- 今年赛题主题是“智慧工厂”，不是上一届“智慧生活”任务。
- 虚拟仿真对应规则里的“子任务 3：仿真系统协同”。
- 子任务 3 不是孤立任务，它发生在实体车完成子任务 2 后：实体车回到对应取货点，发送仿真模拟信号，Gazebo 小车在仿真环境中完成取货、避障、运输、放置，再给实体车返回完成信号。
- 仿真扣分集中在三个点：仓库匹配错误、仿真任务未完成、仿真完成后的播报错误。

## 2. 比赛主流程中仿真的位置

规则中的整体任务链路可以理解为：

```text
语音指令唤醒
-> 子任务 1：前往物品领取区，识别 3 个二维码，调用 Spark X2 筛选目标货品
-> 子任务 2：进入生产区，动态避障，匹配 A/B/C 仓库并语音播报
-> 子任务 3：触发 Gazebo 仿真系统协同
-> 子任务 4：进入停车区，识别交通标志/红绿灯，选择正确路径
-> 子任务 5：视觉巡线，抵达终点并播报“任务完成”
```

仿真子任务的输入来自前两个任务：

- 目标货品类别：食品、日用品、电子产品之一。
- 对应仓库/生产车间：食品加工车间、日用品加工车间、电子产品生产车间之一。
- 实体车到达并播报后，仿真启动。

仿真子任务的输出应该给实体车/裁判：

- Gazebo 小车完成对应物品抓取。
- Gazebo 小车避开锥桶障碍，将物品放到正确仓库/车间。
- 实体车收到完成信号后播报，例如“仿真任务已完成，已将 XX 放入 XX 仓库类别”。

## 3. 子任务 3 的得分与扣分点

规则总分为 100 分，采用扣分制，最低为 0 分。和仿真直接相关的扣分项如下：

| 扣分项 | 判定标准 | 扣分 |
| --- | --- | --- |
| 3.1 仓库匹配错误 | 未抵达正确仓库标识点区域 | -5 |
| 3.2 仿真任务未完成 | 仿真中机械臂未取到正确物品，或未放置到正确仓库 | -5 |
| 3.3 播报错误 | 仿真任务完成后，未按要求格式播报，或播报内容错误 | -10 |

通用扣分项也会影响仿真阶段：

| 通用项 | 判定标准 | 扣分 |
| --- | --- | --- |
| G1 抢跑 | 裁判发令前自动车续跑 | 第一次警告，第二次取消资格 |
| G2 比赛超时 | 总时长达到规定时间仍未完成所有任务 | 按已完成状态计分 |
| G3 未按要求制作电子红绿灯 | 未按规则制作 | -10，最多扣 10 |
| G4 触碰障碍物/挡板/锥桶/红绿灯 | 每次碰撞扣分 | 每次 -5，最多扣 20 |

仿真阶段的核心目标不是“看起来跑了”，而是要保证三件事闭环：

1. 取对物品。
2. 放到对的仓库/车间。
3. 完成后播报格式和内容正确。

## 4. Gazebo 文件夹怎么使用

当前 `Gazebo/` 下有三类资料：

| 路径 | 作用 | 使用方式 |
| --- | --- | --- |
| `gazebo_ws/` | 官方 ROS/Gazebo 工作空间 | 真正运行、编译、调试仿真的地方 |
| `gazebo仿真操作手册.pdf` | 官方操作说明 | 先按手册跑通启动、建图、抓取、释放、摄像头测试 |
| `仿真演示视频.mp4` | 官方演示视频 | 对照检查启动顺序、物块位置、机械臂抓取动作和最终效果 |

建议使用顺序：

1. 先通读本文档，知道为什么要做这些步骤。
2. 按 `gazebo仿真操作手册.pdf` 跑通“能启动、能动、能抓、能放”。
3. 看 `仿真演示视频.mp4`，记录官方演示里的关键姿态和操作节奏。
4. 在 `gazebo_ws/` 里做自己的导航点、机械臂姿态、自动流程脚本。

## 5. `gazebo_ws` 工作空间结构

`gazebo_ws` 是一个 ROS1 catkin 工作空间。它里面最重要的是 `src/`，`build/` 和 `devel/` 是编译产生的结果。

| 文件夹 | 作用 | 新手理解 |
| --- | --- | --- |
| `src/` | 源码区，放 ROS 功能包、launch、脚本、URDF、配置文件 | 主要修改这里 |
| `build/` | 编译中间产物，CMake/catkin 临时文件 | 一般不手改，编译失败时可清理重建 |
| `devel/` | 开发环境产物，含 `setup.bash`、可运行脚本链接、包索引 | 每次新终端运行 ROS 包前要 `source devel/setup.bash` |

常用命令：

```bash
cd "/Users/grififth/Documents/Competitions/Smart car/iflytek-smart-car/Gazebo/gazebo_ws"
catkin_make
source devel/setup.bash
```

注意：如果是在 Ubuntu 车端或虚拟机里运行，需要把路径换成对应机器上的真实路径。

## 6. `src/` 中各功能包作用

| 包 | 作用 | 重点文件 |
| --- | --- | --- |
| `car3` | 车辆模型、机械臂、夹爪、Gazebo 场景、物块/锥桶生成、伪抓取节点 | `launch/gazebo.launch`、`world/math.world`、`urdf/car3.urdf`、`scripts/spawn_cubes.py`、`scripts/grasp_attach.py` |
| `gazebo_nav` | 导航功能，包含 `move_base`、AMCL、代价地图、DWA 参数 | `launch/gazebo_nav.launch`、`launch/config/move_base/*.yaml` |
| `gazebo_map` | 建图功能，使用 `gmapping` | `launch/gmapping.launch` |
| `roboticsgroup_gazebo_plugins` | Gazebo 机械臂/关节相关插件 | 一般不改，只保证能编译 |

必须注意：

- `car3/scripts/spawn_cubes.py` 手册明确说比赛时裁判会查看，不可以修改。它负责随机生成 3 个物块和 10 个锥桶。
- 当前 `gazebo_nav/launch/gazebo_nav.launch` 已使用 `$(find gazebo_map)/maps/math.yaml`，RViz 配置默认为 `$(env HOME)/gazebo_ws/src/rviz_default_config.rviz`。
- 当前源码中已查无 `/home/ucar/...` 和 `/home/howard/...` 残留路径；如从官方原始压缩包重新覆盖源码，仍需按第 13 节重新检查。
- `car3/world/math.world` 中 `<shadows>` 当前已为 `0`，可降低 Gazebo 图形渲染负担。

## 7. 零基础 Ubuntu 使用方式

你现在面对的是一台从未使用过的 Ubuntu 电脑。不要急着运行 Gazebo，先熟悉最少量的命令行操作。后面所有仿真都靠终端启动。

### 7.1 打开终端

常用方法：

- 按 `Ctrl + Alt + T`。
- 或点击左下角/左侧应用菜单，搜索 `Terminal`。

终端打开后会看到类似：

```text
用户名@电脑名:~$
```

其中 `~` 代表当前用户的家目录，例如 `/home/ucar` 或 `/home/你的用户名`。

### 7.2 命令行基本规则

- 文档里的命令一行一行复制执行。
- 不要复制命令前面的说明文字。
- 输入命令后按回车。
- 密码输入时终端不会显示星号，这是正常的，输完按回车即可。
- 命令运行卡住或想停止，按 `Ctrl + C`。
- 终端内容太多，可以按 `Ctrl + L` 清屏。
- 路径或命令输入一半，可以按 `Tab` 自动补全。
- 复制到终端通常用 `Ctrl + Shift + V`，不是 `Ctrl + V`。

### 7.3 必会命令

| 命令 | 作用 | 示例 |
| --- | --- | --- |
| `pwd` | 查看当前在哪个文件夹 | `pwd` |
| `ls` | 查看当前文件夹内容 | `ls` |
| `ls -l` | 查看详细内容 | `ls -l` |
| `cd` | 进入某个文件夹 | `cd ~/gazebo_ws` |
| `cd ..` | 回到上一级文件夹 | `cd ..` |
| `mkdir` | 新建文件夹 | `mkdir -p ~/catkin_ws/src` |

| `gedit` | 用图形文本编辑器打开文件 | `gedit 文件名` |

第一次建议优先用 `gedit` 改文件，因为它是图形界面编辑器，比 `vim` 友好很多。

### 7.4 先确认 Ubuntu 版本

在终端输入：

```bash

```

重点看 `Description` 和 `Release`。

推荐环境：

### 7.5 你当前 Ubuntu 22.04 主机能不能跑这个仿真

你的 Ubuntu 主机经检查是：

```text
Ubuntu 22.04.5 LTS
代号 jammy
```

结论：

- 不是“绝对不能做 Gazebo 仿真”。
- 但是不适合按官方 `gazebo_ws` 的 ROS1 Noetic 路线直接做。
- 本项目官方包是 ROS1 catkin 工作空间，手册命令也是 `ros-noetic-*`、`catkin_make`、`roslaunch` 这一套。
- ROS Noetic 的标准二进制安装目标是 Ubuntu 20.04，而 Ubuntu 22.04 对应的是 ROS2 Humble 或从源码折腾 ROS1，这对新手和备赛都不划算。

所以不建议在这台 Ubuntu 22.04 主机上继续直接安装 ROS Noetic/Gazebo 仿真环境。更稳的选择：

| 方案 | 推荐程度 | 说明 |
| --- | --- | --- |
| 原生 Ubuntu 20.04 电脑/双系统 | 最推荐 | 图形界面、Gazebo、RViz、USB/硬件支持最稳 |
| Windows + WSL2 Ubuntu 20.04 | 可以尝试 | 适合学习、调试、跑仿真；Gazebo 图形界面取决于 Windows/WSLg/X server |
| Ubuntu 22.04 上 Docker 跑 20.04 | 不建议新手优先 | 网络、图形、权限配置更复杂 |
| Ubuntu 22.04 上迁移 ROS2 | 不建议 | 官方包要迁移，工作量大 |

### 7.6 如果改用 Windows + Ubuntu 20.04 WSL，大致流程

如果另一台 Windows 电脑已经安装了 Ubuntu 20.04 的 WSL，可以按下面顺序推进。

先判断 Windows 和 WSL 情况。在 Windows 里打开 PowerShell，执行：

```powershell
wsl -l -v
wsl --status
```

重点看：

- Ubuntu 版本是不是 `Ubuntu-20.04`。
- WSL 版本是不是 `2`。
- Windows 是 Windows 11 还是 Windows 10。

推荐：

- Windows 11 + WSL2：优先，因为有 WSLg，通常可以直接打开 Linux GUI 程序。
- Windows 10 + WSL2：也能做，但通常需要额外安装 X server，例如 VcXsrv，图形配置麻烦一些。

WSL 路线总流程：

```text
Windows 端确认 WSL2 和 Ubuntu 20.04
-> WSL 里确认图形界面能打开
-> WSL 里安装 ROS Noetic 和 Gazebo 依赖
-> 把 gazebo_ws 放进 WSL 的 Linux 家目录
-> 修官方包里的本地路径
-> catkin_make 编译
-> 先临时关闭导航，启动 Gazebo 场景
-> 键盘控制小车
-> 建图保存 math.yaml
-> 恢复导航，RViz 发目标点测试
```

第一步先在 WSL Ubuntu 20.04 里检查系统版本：

```bash
cat /etc/os-release
```

应该看到：

```text
VERSION_ID="20.04"
VERSION_CODENAME=focal
```

第二步先测试 WSL 图形界面。安装测试工具：

```bash
sudo apt update
sudo apt install -y x11-apps mesa-utils
```

测试普通图形窗口：

```bash
xeyes
```

如果能弹出一双眼睛，说明基础 GUI 可用。关掉窗口继续。

测试 OpenGL：

```bash
glxinfo -B
```

如果能输出显卡/OpenGL 信息，说明图形环境比较健康。

如果 `xeyes` 都打不开：

- Windows 11：先在 PowerShell 里执行 `wsl --update`，重启 WSL 或重启电脑后再试。
- Windows 10：通常需要安装并启动 VcXsrv，再配置 `DISPLAY`，这条路线对新手更麻烦。

第三步再安装 ROS Noetic。后续从本文第 8 节开始执行即可，但路径都以 WSL 的 Linux 路径为准，例如：

```text
/home/你的WSL用户名/gazebo_ws
```

不要把 `gazebo_ws` 直接放在 Windows 的 `C:\` 目录里运行。WSL 里访问 `/mnt/c/...` 会比较慢，也容易出现权限/换行/路径问题。建议复制到 WSL 家目录：

```bash
cp -r /mnt/c/Users/你的Windows用户名/Downloads/gazebo_ws ~/
cd ~/gazebo_ws
```

如果用 Windows 文件管理器复制，也可以在地址栏输入：

```text
\\wsl$\Ubuntu-20.04\home\你的WSL用户名
```

然后把 `gazebo_ws` 拖进去。

WSL 路线的注意事项：

- Gazebo/RViz 是图形程序，先测试 `xeyes`，再测试 Gazebo。
- WSL 适合先学习和跑仿真，但如果以后要接真实小车 USB、串口、雷达，相比原生 Ubuntu 会更麻烦。
- 如果 Gazebo 窗口能打开但很卡，先按本文后面的方法关闭 `math.world` 里的阴影。
- 如果 Windows 电脑性能一般，WSL 跑 Gazebo 可能比原生 Ubuntu 慢。

## 8. 新电脑环境安装总流程

这一节目标：把一台新 Ubuntu 电脑装成可以运行 `gazebo_ws` 的仿真电脑。

### 8.1 联网检查

先确认电脑能上网：

```bash
ping -c 4 baidu.com
```

如果能看到类似 `4 received` 或有多行时间 `time=... ms`，说明网络通。

如果提示无法解析域名或 100% 丢包：

- 检查 Wi-Fi/网线。
- 打开浏览器访问网页。
- 确认学校网络是否需要网页登录认证。

### 8.2 更新软件列表

```bash
sudo apt update
```

如果提示输入密码，输入 Ubuntu 登录密码。

如果出现 `Could not get lock`：

- 说明系统更新程序正在运行。
- 等几分钟，或关闭“软件更新器”窗口后重试。

### 8.3 安装基础工具

```bash
sudo apt install -y curl wget git gedit nano vim net-tools build-essential cmake python3-pip
```

这些工具的作用：

- `git`：以后下载代码用。
- `gedit/nano/vim`：改配置文件用。
- `build-essential/cmake`：编译 ROS 包用。
- `python3-pip`：安装 Python 依赖用。
- `net-tools`：查看 IP 等网络信息用。

## 9. 安装 ROS Noetic

这一节只适用于 Ubuntu 20.04。如果 `lsb_release -a` 显示不是 20.04，先不要硬装。

### 9.1 添加 ROS 软件源

```bash
sudo sh -c 'echo "deb http://packages.ros.org/ros/ubuntu $(lsb_release -sc) main" > /etc/apt/sources.list.d/ros-latest.list'
```

添加密钥：

```bash
curl -s https://raw.githubusercontent.com/ros/rosdistro/master/ros.asc | sudo apt-key add -
```

更新软件列表：

```bash
sudo apt update
```

### 9.2 安装 ROS Noetic 桌面完整版

```bash
sudo apt install -y ros-noetic-desktop-full
```

这一步会比较久，因为它会安装：

- ROS 核心命令。
- RViz。
- Gazebo 相关组件。
- 常见机器人消息、工具和库。

### 9.3 配置 ROS 环境变量

每次打开终端都需要加载 ROS 环境。为了不每次手打，把它写入 `~/.bashrc`：

```bash
echo "source /opt/ros/noetic/setup.bash" >> ~/.bashrc
source ~/.bashrc
```

验证 ROS 是否安装成功：

```bash
roscore
```

如果看到类似：

```text
started core service [/rosout]
```

说明 ROS 核心可以启动。

停止 `roscore`：

```text
按 Ctrl + C
```

### 9.4 安装 catkin 编译工具

```bash
sudo apt install -y python3-rosdep python3-rosinstall python3-rosinstall-generator python3-wstool python3-catkin-tools
```

初始化 `rosdep`：

```bash
sudo rosdep init
rosdep update
```

如果 `sudo rosdep init` 提示已经存在，不是严重问题，可以继续执行 `rosdep update`。

如果 `rosdep update` 因网络失败，多试几次；学校网络或 GitHub 访问不稳定时它可能会失败。

### 14.2 显式使用 NVIDIA GPU 启动 Gazebo 场景

当前这台机器是 WSL2/WSLg 图形环境。实测普通执行 `glxinfo -B` 会落到 `llvmpipe`，这是 CPU 软件渲染；必须显式选择 D3D12 和 NVIDIA 适配器。

启动前先在当前终端设置：

```bash

export MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA
export LIBGL_ALWAYS_SOFTWARE=0
```

然后强制验收 OpenGL 渲染器：

```bash
glxinfo -B | grep -E 'Device|Accelerated|OpenGL renderer'
```

当前机器的正确输出应包含：

```text
Device: D3D12 (NVIDIA T600 Laptop GPU)
Accelerated: yes
OpenGL renderer string: D3D12 (NVIDIA T600 Laptop GPU)
```

如果仍显示 `llvmpipe` 或 `Accelerated: no`，不要继续启动 Gazebo，先按第 18.10 节排查 GPU 环境。

验收通过后，仍在同一个终端启动：

```bash
roslaunch car3 gazebo.launch gui:=true
```

也可以写成一条显式命令，效果相同：

```bash
GALLIUM_DRIVER=d3d12 \
MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA \
LIBGL_ALWAYS_SOFTWARE=0 \
roslaunch car3 gazebo.launch gui:=true
```

这些环境变量会传给 `gzclient`/`gzserver` 子进程。GPU 主要负责 Gazebo GUI 与相机等渲染；Gazebo 物理计算仍主要使用 CPU，而当前 URDF 中激光雷达是 `<sensor type="ray">`，不是 `gpu_ray`。

第一次启动可能比较慢，等 1-3 分钟是正常的。

成功后应该看到：

- Gazebo 图形窗口打开。
- 场地出现。
- 小车模型出现。
- 机械臂和夹爪出现。
- 3 个随机物块出现。

终端中可能有一些 warning，不一定影响运行。重点看有没有红色 `ERROR`，以及 Gazebo 窗口里模型是否出现。

新开终端：

发送一个参考姿态：

- 用键盘微调车的位置。
- 或微调机械臂姿态。
- 或查看偏移量。

### 19.4 闭合夹爪抓取

## 23. 比赛中如何自动触发仿真流程

规则图里说“子任务 2 的语音播报完成后，自动触发”，这句话在工程实现上可以理解为：实体车主状态机在完成子任务 2 后，向仿真任务节点发送一个“开始仿真任务”的消息；仿真任务节点收到消息后开始执行 Gazebo 中的导航、抓取、搬运、放置；执行成功后再发回一个“仿真完成”的消息，实体车主状态机收到后播报并进入子任务 4。

这个“发送信号”不是神秘硬件信号，最简单就是 ROS 里的消息。可以用 topic、service 或 action 实现。

### 23.1 推荐的最小闭环：ROS topic

初学和备赛阶段建议先用 ROS topic，因为它最容易调试：

| 方向 | 话题名建议 | 消息类型 | 作用 |
| --- | --- | --- | --- |
| 实体车/主状态机 -> Gazebo 仿真节点 | `/sim_task/start` | `std_msgs/String` | 通知仿真开始，并携带目标类别 |
| Gazebo 仿真节点 -> 实体车/主状态机 | `/sim_task/status` | `std_msgs/String` | 回报仿真状态，例如 running/done/failed |
| Gazebo 仿真节点 -> 实体车/主状态机 | `/sim_task/result` | `std_msgs/String` | 回报最终结果，包含物品和仓库类别 |

示例消息内容先用简单字符串即可：

```text
food
daily
electronics
```

也可以用更完整的 JSON 字符串：

```json
{"task_id":"task3","target_class":"food","target_item":"banana","warehouse":"food"}
```

第一阶段建议先用简单字符串，跑通后再升级 JSON。

### 23.2 最小人工测试流程

在没有实体车状态机时，可以用命令行模拟“子任务 2 已完成，触发仿真”。

终端 1：启动 Gazebo。

```bash
cd ~/gazebo_ws
source devel/setup.bash
roslaunch car3 gazebo.launch
```

终端 2：启动你后续要写的仿真任务节点，名字可以先叫 `sim_task_node.py`。

```bash
cd ~/gazebo_ws
source devel/setup.bash
rosrun car3 sim_task_node.py
```

终端 3：模拟实体车发布开始信号。

```bash
rostopic pub /sim_task/start std_msgs/String "data: 'food'" -1
```

终端 4：监听仿真状态。

```bash
rostopic echo /sim_task/status
```

如果仿真节点收到 `food` 后开始动作，并最终输出 `done`，就说明触发链路成立。

### 23.3 比赛时的状态机流程

实体车主状态机建议按下面逻辑写：

```text
子任务 2：到达目标仓库标识点
-> 语音播报“已将 XX 放入 XX”
-> 发布 /sim_task/start，内容为目标类别
-> 进入 WAIT_SIM_DONE 状态
-> 持续监听 /sim_task/status 或 /sim_task/result
-> 收到 done/result 后，播报“仿真任务已完成，已将 XX 放入 XX 仓库类别”
-> 进入子任务 4：交通决策与路径选择
```

关键点：

- 发布 `/sim_task/start` 前，必须确认子任务 2 的播报已经完成。
- 发布开始信号后，实体车不要继续乱跑，应进入等待状态。
- 等待时可以设置超时，例如 60-120 秒。如果超时没有收到完成信号，进入失败处理或人工策略。
- 收到完成信号后，播报内容要按规则要求组织，避免 3.3 播报错误扣 10 分。

### 23.4 Gazebo 仿真节点内部逻辑

Gazebo 侧需要一个“仿真任务节点”，它负责订阅开始信号、执行动作、发布结果。逻辑如下：

```text
启动节点
-> 订阅 /sim_task/start
-> 等待目标类别
-> 收到 food/daily/electronics
-> 发布 /sim_task/status = running
-> 判断目标物块和目标仓库
-> 导航到对应物块区域
-> 调机械臂抓取
-> 检查 /grasp_attach/state 是否为 GRASPING
-> 导航到对应仓库/车间区域
-> 打开夹爪释放
-> 检查释放成功
-> 发布 /sim_task/status = done
-> 发布 /sim_task/result
```

伪代码：

```python
def on_start(msg):
    target_class = msg.data
    publish_status("running")

    ok = run_sim_task(target_class)

    if ok:
        publish_status("done")
        publish_result(f"done:{target_class}")
    else:
        publish_status("failed")
```

### 23.5 三种通信方式的取舍

| 方式 | 优点 | 缺点 | 当前建议 |
| --- | --- | --- | --- |
| topic | 最简单，命令行好调试 | 没有请求/响应确认，消息可能错过 | 第一阶段使用 |
| service | 一问一答，适合“开始任务”这种命令 | 长时间任务不适合一直阻塞 | 第二阶段可用于开始命令 |
| action | 最适合长任务，有反馈、取消、结果 | 写法比 topic/service 复杂 | 后期稳定后再考虑 |

推荐路线：

```text
第 1 版：topic 跑通 start/status/result
第 2 版：start 改 service，status/result 保留 topic
第 3 版：如果时间充足，再改 action
```

### 23.6 单机仿真和实体车联动的区别

在寝室单机做仿真时：

```text
命令行 rostopic pub /sim_task/start
-> Gazebo 仿真节点执行
-> rostopic echo /sim_task/status 看结果
```

在实验室实体车联动时：

```text
实体车主状态机发布 /sim_task/start
-> Gazebo 仿真节点执行
-> 实体车主状态机监听 /sim_task/status
-> 实体车播报并进入后续任务
```

如果实体车和 Gazebo 在同一台电脑上，ROS 通信最简单，直接用同一个 `roscore`。

如果实体车和 Gazebo 在两台电脑上，需要配置 ROS 多机通信：

- 两台电脑在同一局域网。
- 能互相 `ping` 通。
- 设置同一个 `ROS_MASTER_URI`。
- 各自设置正确的 `ROS_IP`。

多机通信更容易出网络问题，所以第一阶段强烈建议先在一台电脑上把单机闭环跑通。

### 23.7 你需要具体做什么

当前阶段按这个顺序做：

1. 先不用实体车，在 Gazebo 电脑上手动发布 `/sim_task/start`。
2. 写一个最小 `sim_task_node.py`，收到 `food/daily/electronics` 后先只打印并发布 `running/done`。
3. 确认 topic 触发链路稳定。
4. 再把 `sim_task_node.py` 里的空动作替换成真实导航、抓取、释放。
5. 最后把实体车主状态机接入 `/sim_task/start` 和 `/sim_task/status`。

最小验证标准：

```text
rostopic pub /sim_task/start std_msgs/String "data: 'food'" -1
-> /sim_task/status 输出 running
-> 若干秒后 /sim_task/status 输出 done
```

达到这个标准后，再继续做真实动作。

## 24. 第四阶段：自动化仿真任务方案

最终比赛需要从“人工能跑”升级到“自动或半自动稳定完成”。建议路线：

1. 建立任务状态机。

```text
WAIT_SIM_TRIGGER
-> IDENTIFY_TARGET_CLASS
-> NAV_TO_TARGET_CUBE_AREA
-> FINE_ALIGN_FOR_GRASP
-> ARM_GRASP
-> VERIFY_GRASPING
-> NAV_TO_TARGET_WAREHOUSE
-> ARM_RELEASE
-> VERIFY_RELEASE
-> PUBLISH_SIM_DONE
```

2. 输入目标类别。

目标类别来自实体车前序任务，先用命令行模拟：

```text
food / daily / electronics
```

后续再改成 ROS topic 或 service。

3. 物块类别映射。

官方仿真会生成 3 个贴图物块：

- 食品。
- 日用品。
- 电子产品。

需要确认 `model_0.sdf`、`model_1.sdf`、`model_2.sdf` 分别对应哪张贴图。不要修改 `spawn_cubes.py`，只在自己的任务脚本里读取/记录类别映射。

4. 导航策略。

先不要一上来追求完全自主识别随机物块坐标。推荐分三步：

- 第一步：手工记录 3 个物块生成区域的导航候选点。
- 第二步：导航到候选点后，用 `/grasp_attach/offset` 和机械臂固定姿态做微调。
- 第三步：再考虑用摄像头识别贴图或 Gazebo 服务读取模型坐标，提高自动化程度。

5. 抓取策略。

抓取成功以 `/grasp_attach/state` 输出 `GRASPING` 为准，不要只看夹爪命令是否发出。

6. 放置策略。

放置成功至少满足：

- 小车到达正确仓库/车间标识点区域。
- 夹爪打开。
- `/grasp_attach/state` 从 `GRASPING` 回到 `IDLE`。
- 物块位置落在目标区域附近。

7. 完成信号与播报。

完成后向实体车状态机发送 `sim_done`，实体车播报必须包含：

- 仿真任务已完成。
- 目标物品名称。
- 放入的仓库/车间类别。

避免 3.3 的 -10 分。

## 27. 注意事项与红线

必须遵守：

- 不修改 `car3/scripts/spawn_cubes.py`，手册明确说比赛时裁判会查看。
- 不把联网、大模型、云端识别用于仿真导航、抓取、避障或行驶决策。
- 仿真任务完成后要按要求播报，播报内容错误扣分比仿真失败还重。
- 遇到路径问题，优先修本地绝对路径和 `source devel/setup.bash`，不要盲目改源码。
- 每次打开新终端都要进入工作空间并 `source devel/setup.bash`。
- 先保证手动稳定，再做自动化；不要同时改导航、机械臂、地图和状态机。

常见故障：

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `RobotModel` 不显示 | 没有 source 环境 | `source devel/setup.bash` |
| Gazebo 打不开或卡死 | 阴影/显卡/模型加载问题 | 将 `math.world` 中 `<shadows>` 改为 `0` |
| 物块/仓库贴图丢失 | `file:///home/ucar/...` 路径不对 | 改为本机真实路径 |
| 导航启动失败 | 地图 `math.yaml` 路径不对 | 重新建图并修改 `gazebo_nav.launch` |
| RViz 报配置文件不存在 | `/home/howard/Desktop/20.rviz` 不存在 | 去掉 `args` 或改成本机 RViz 配置 |
| 夹爪闭合但没抓到 | TCP 未进入物块范围 | 看 `/grasp_attach/ready` 和 `/grasp_attach/offset` |
| 抓到后抖动 | 伪抓取物理模拟正常现象 | 轻微抖动不影响搬运 |
