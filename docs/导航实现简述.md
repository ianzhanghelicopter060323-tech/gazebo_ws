## 4 代码实现简述

### 4.1 Mission 与导航 Action 的边界

总任务编排仍位于
`src/smart_factory_mission/src/smart_factory_mission/mission_server.py`，但它不再
直接拥有定位检查、路线跟踪或底盘对齐实现。Mission 通过
`NavigationClient` 调用 `/smart_factory/navigation` 上的 `NavigateAction`；对应
Action Server 及导航实现均位于 `src/smart_factory_navigation/`：

- `action_server.py`：接收 `NavigateGoal`，统一管理导航侧可变状态；
- `localization_monitor.py`：检查 AMCL、TF、新鲜度和协方差；
- `route_executor.py`：执行整条路线、超时重试和航向约束；
- `path_tracker.py`：计算拟合路径进度和曲率自适应前视点；
- `base_alignment_controller.py`：执行抓取前的底盘低速精对齐；
- `navigation_stage.py`：封装标准 `move_base_msgs/MoveBaseAction`。

两个 Action 的职责不同：`/sim_task/execute` 是外部任务接口，Mission 负责状态机、
感知和抓取流程协调；`/smart_factory/navigation` 是内部导航子系统接口，负责定位、
路线执行、单点导航和底盘对齐。

### 4.2 拟合路径加载与跟踪

Mission 启动时读取 `mission.yaml` 和开发锚点
`smart_factory_mission/config/pickup_staging_dev.yaml`。导航 Action Server 启动时则
读取：

```text
src/smart_factory_navigation/config/navigation.yaml
src/smart_factory_navigation/config/pickup_staging_fitted_path.yaml
```

- 当前 `route_execution_mode` 在 `navigation.yaml` 中配置为
  `fitted_path_lookahead`。`RouteExecutor` 将已生成的拟合结果转换成
  `nav_msgs/Path`，发布到 `/sim_task/reference_path`。
- `PathTracker` 根据 `/amcl_pose` 和 `map -> base_footprint` TF 得到机器人
  当前位置，将其投影到参考路径，并只允许进度 `s` 单调增加，避免在弯道跳回
  前面的路径段。
- 跟踪目标是参考路径前方的一小段 `lookahead`。曲率较大时减小前视距离，
  曲率较小时增大前视距离，当前范围为 `0.20 m` 到 `0.50 m`。
- 特殊直线段和 `heading_locks` 同样在 `navigation.yaml` 中配置。当前
  `21 -> 22` 为直线段，部分弯道会逐渐锁定车头方向，并在区段末端前释放。

跟踪过程中由导航 Action Server 发布：

- `/sim_task/reference_path`：完整拟合参考路径；
- `/sim_task/tracking_goal`：当前发送给 `move_base` 的前视目标；
- `/sim_task/path_progress`：机器人在路径上的累计弧长进度。

拟合路径不会在任务运行时重新计算。修改
`src/smart_factory_mission/config/pickup_staging_dev.yaml` 中的有效导航点后，需要
重新运行 `plot_fitted_navigation_path.py`，生成
`src/smart_factory_navigation/config/pickup_staging_fitted_path.yaml`，再重启导航
Action Server 或 `full_competition.launch` 验证。

路径数据流可以概括为：

```text
pickup_staging_dev.yaml
        |
        |  plot_fitted_navigation_path.py 离线拟合
        v
smart_factory_navigation/config/pickup_staging_fitted_path.yaml
        |
        |  NavigationActionServer / RouteExecutor 读取并发布
        v
/sim_task/reference_path
        |
        |  PathTracker 根据 AMCL / TF 计算进度和前视点
        v
/sim_task/tracking_goal  --->  move_base
```

### 4.3 任务状态机与定位检查

任务服务器通过 `/sim_task/execute` 接收 `ExecuteTaskAction`。收到任务后依次：

1. 检查 `task_id` 和 `target_class`；
2. 等待 `/smart_factory/navigation` Action Server；
3. 发送 `WAIT_FOR_LOCALIZATION`，由导航侧检查 AMCL 和 TF；
4. 从 `pickup_staging_dev.yaml` 获取当前开发路线锚点；
5. 发送 `EXECUTE_STAGING_ROUTE` 和锚点列表；
6. 将 Navigate feedback、结果和错误码映射回 Mission 状态机。

定位检查仍只使用 AMCL 和 TF，不读取 `/gazebo/model_states` 等 Gazebo 真值。
机器人静止时 `/amcl_pose` 时间戳可能不更新；如果实时 TF 仍然有效，可按
`navigation.yaml` 的配置允许使用新鲜 TF 作为补充判断。

Mission 状态发布到 `/sim_task/state`，外部客户端可从
`/sim_task/execute/feedback` 观察任务阶段。导航内部的当前路径点、重试次数、
路径进度和说明由 `/smart_factory/navigation/feedback` 返回，再由 Mission 转换为
外部任务反馈。

### 4.4 机器人导航执行

`src/smart_factory_navigation/src/smart_factory_navigation/navigation_stage.py`
将目标封装成 `MoveBaseGoal` 发送到 `/move_base`，原有运行行为保持不变：

- 中间路径点进入 `intermediate_pass_radius`（当前为 `0.20 m`）后即可切换，
  不要求逐点停车；
- 相邻前视目标通过新的 `send_goal` 替换旧目标，避免“取消—停车—再发送”造成
  额外停顿；
- 只有最终目标要求 `move_base` 返回 `SUCCEEDED`；目标超时、Action 拒绝、
  规划失败或任务取消时，由 `RouteExecutor` 处理取消、重试或失败；
- 当前单目标超时 `60 s`、最大重试 `1` 次、完整路线超时 `240 s`。

启用航向约束时，`RouteExecutor` 会在进入指定位置范围后取消当前 `move_base`
目标，再依据 `map -> base_footprint` 计算角度差并向 `/cmd_vel` 发布有限角速度。
抓取前的低速平移由同一 Action Server 内的 `BaseAlignmentController` 负责。这些
直接底盘控制均属于导航子系统，不属于 Mission 状态机。

完整控制链路为：

```text
/sim_task/execute (ExecuteTaskAction)
        |
        v
MissionServer（任务编排）
        |
        |  /smart_factory/navigation (NavigateAction)
        v
NavigationActionServer
        |
        +--> LocalizationMonitor <--- AMCL / TF
        |
        +--> RouteExecutor / PathTracker ---> MoveBaseGoal
                                             |
                                             v
                          move_base + GlobalPlanner + TebLocalPlannerROS
                                             |
                                             v
                         局部代价地图读取 /scan，输出 /cmd_vel
```

路径规划和动态避障仍由 `move_base`、代价地图和 TEB 局部规划器完成。导航
Action Server 负责目标更新、超时重试、路径进度及必要的底盘对齐；Mission 只
负责业务状态编排以及导航结果到 `ExecuteTaskResult` 的语义映射。

## 6 本工作空间除基本ROS环境外的依赖

- 本工程按```ROS Noetic + Ubuntu 20.04```环境开发，除了基本 ROS 环境外，导航仿真至少需要以下 ROS 包：

  ```bash
  sudo apt install -y \
    ros-noetic-gazebo-ros-pkgs \
    ros-noetic-gazebo-ros-control \
    ros-noetic-ros-control \
    ros-noetic-ros-controllers \
    ros-noetic-navigation \
    ros-noetic-map-server \
    ros-noetic-amcl \
    ros-noetic-move-base \
    ros-noetic-gmapping \
    ros-noetic-robot-state-publisher \
    ros-noetic-joint-state-publisher-gui \
    ros-noetic-tf \
    ros-noetic-tf2-tools
  ```

- 工作空间编译需要```catkin_make```及其构建工具。若系统尚未安装，可以补充：

  ```bash
  sudo apt install -y build-essential cmake python3-catkin-tools python3-rosdep
  ```

- 路径拟合脚本```src/gazebo_map/scripts/plot_fitted_navigation_path.py```不是 ROS 节点，依赖 Python 3 的以下第三方库：

  - ```numpy```：路线平滑、样条拟合和曲率计算；
  - ```Pillow```：绘制拟合路径示意图；
  - ```PyYAML```：读取和写入路线 YAML 配置。

  Ubuntu 环境可以直接安装对应系统包：

  ```bash
  sudo apt install -y python3-numpy python3-pil python3-yaml
  ```

  也可以使用 pip 安装当前用户环境中的同名包：

  ```bash
  python3 -m pip install --user numpy Pillow PyYAML
  ```

- 任务状态机和单元测试使用 Python 标准库```unittest```；通过 catkin 测试时还需要```python3-nose```：

  ```bash
  sudo apt install -y python3-nose
  ```

- 本工程自带```roboticsgroup_gazebo_plugins```源码包，因此不需要另外下载同名插件。它会在```catkin_make```时编译生成 Gazebo 机械臂关节相关插件。

- 如果只运行已经生成好的导航路线，不需要安装 SciPy；当前拟合程序使用 NumPy 自己实现正则化和自然三次样条计算。只有在修改拟合程序时，才需要额外注意 NumPy、Pillow 和 PyYAML 是否能够正常导入。

- 安装完成后，进入工作空间重新编译并加载环境：

  ```bash
  cd /home/ianichinose/gazebo_ws
  source /opt/ros/noetic/setup.bash
  catkin_make
  source devel/setup.bash
  ```
