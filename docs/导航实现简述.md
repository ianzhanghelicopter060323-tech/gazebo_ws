## 4 代码实现简述

### 4.1 路径发布

路径发布和任务执行的主要代码在
```/home/ianichinose/gazebo_ws/src/smart_factory_mission/src/smart_factory_mission/mission_server.py```
中，路径几何处理在同目录下的```path_tracker.py```中。

- 任务服务器启动时会读取```mission.yaml```和```pickup_staging_fitted_path.yaml```。

- 任务系统只保留拟合路径自适应导航。任务开始时，系统会将离线拟合结果转换成```nav_msgs/Path```，一次性发布到```/sim_task/reference_path```。这个话题是任务服务器内部使用的参考路径，主要用于路径跟踪和 RViz 可视化，并不是```move_base```直接读取的全局规划路径。

- ```PathTracker```根据```/amcl_pose```和```map -> base_footprint``` TF得到的机器人当前位置，将机器人投影到参考路径上，并且只允许路径进度```s```单调增加，避免机器人在弯道处跳回前面的路径段。

- 路径跟踪目标不是固定不变的终点，而是参考路径前方的一小段```lookahead```目标。曲率较大时减小前视距离，曲率较小时增大前视距离，当前配置范围为```0.20 m```到```0.50 m```。任务服务器会根据机器人实时位置持续计算这个前视目标，并按距离或时间周期更新发送给```move_base```。

- 跟踪过程中会发布以下参考和调试话题：

  - ```/sim_task/reference_path```：完整拟合参考路径；
  - ```/sim_task/tracking_goal```：当前发送给```move_base```的前视目标；
  - ```/sim_task/path_progress```：机器人在路径上的累计弧长进度。

- 在```mission.yaml```中可以配置特殊路径段。当前```21 -> 22```配置为直线段，部分弯道可通过```heading_locks```逐渐锁定车头方向，再在到达区段末端前释放，避免急转时车头摆动。

- 拟合路径不是运行时重新计算的。修改```pickup_staging_dev.yaml```中的有效导航点后，需要重新运行```plot_fitted_navigation_path.py```生成新的```pickup_staging_fitted_path.yaml```，再启动任务服务器验证。

因此，当前导航设计不是“将完整拟合路径一次性交给```move_base```执行”，而是“发布固定参考路径，再持续更新前视导航目标”。路径发布和跟踪过程可以概括为：

```text
pickup_staging_dev.yaml
        |
        |  plot_fitted_navigation_path.py 离线拟合
        v
pickup_staging_fitted_path.yaml
        |
        |  MissionServer 读取并发布
        v
/sim_task/reference_path
        |
        |  PathTracker 根据 AMCL 位姿计算进度和前视点
        v
/sim_task/tracking_goal
        |
        |  MissionServer 按距离或时间更新 MoveBaseGoal
        v
move_base 对当前前视目标重新进行全局规划和局部规划
```

### 4.2 任务状态机与定位检查

任务服务器通过```/sim_task/execute```接收```ExecuteTaskAction```。收到任务后，不会立即发送导航目标，而是依次执行：

1. 检查```task_id```和```target_class```是否有效；
2. 等待```/move_base``` Action 服务；
3. 检查```/amcl_pose```是否存在、协方差是否在阈值内；
4. 检查```map -> base_footprint``` TF是否存在且足够新；
5. 读取当前开发阶段的抓取区前置路线；
6. 开始发布参考路径并执行导航。

定位检查使用的是 AMCL 和 TF，不读取```/gazebo/model_states```等 Gazebo 真值。机器人静止时```/amcl_pose```时间戳可能不更新，此时只要实时 TF 仍然有效，可以按照配置允许使用新鲜 TF 作为补充判断。

任务状态会同时发布到```/sim_task/state```，Action 客户端可以从```/sim_task/execute/feedback```观察当前阶段、重试次数和详细信息。

### 4.3 机器人导航执行

本节按照“路径进度```s```—前视距离—移动目标”的逻辑说明机器人如何沿拟合路线行驶。

#### 4.3.1 拟合路径不是一组需要逐个停车的目标点

拟合程序把手动记录的导航点转换成一条连续的参考路线。YAML 中的```points```只是这条连续路线的离散表示，每个离散点包含：

- ```x```、```y```：路径位置；
- ```yaw```：路径在该位置的期望朝向；
- ```s```：从路径起点沿路径累计到该位置的距离；
- ```curvature```：该位置附近的曲率。

因此，路径点应理解为：

```text
一条连续路线的离散采样点
```

而不是：

```text
一串需要机器人逐个到达并停车的独立 MoveBaseGoal
```

运行时，```MissionServer```会将完整拟合结果发布为```nav_msgs/Path```到```/sim_task/reference_path```，便于可视化和调试。```move_base```并不直接接收这条完整```Path```，真正发送给```move_base```的是任务服务器根据当前进度计算出来的单个位姿目标。

#### 4.3.2 获取机器人当前位置并计算路径进度

机器人当前位姿由定位系统提供。任务开始前，系统检查```/amcl_pose```、定位协方差以及```map -> base_footprint``` TF是否有效；执行跟踪时，通过TF取得机器人在```map```坐标系中的```x```、```y```位置。

任务服务器每个控制周期执行以下逻辑：

```text
读取机器人当前位置 (x, y)
        |
        v
在拟合路径上寻找机器人当前位置的投影点
        |
        v
得到投影点对应的路径距离 s
```

这里的```s```类似“沿规划路径的里程”，但它不是车轮里程计。它是把机器人当前位置投影到参考路径后得到的路径进度，表示机器人沿参考路线大约走到了哪里。

例如：

```text
当前 progress_s = 2.40 m
```

表示机器人当前位于距离拟合路径起点约```2.40 m```的路径位置。

路径跟踪器要求```s```单调增加：

```text
上一次 progress_s = 2.40 m
本次投影结果     = 2.35 m
采用的进度       = 2.40 m
```

这样可以避免AMCL或TF的微小抖动使机器人被错误判断为回到了已经走过的路径段。投影时还限制在当前进度前方的搜索窗口内，避免在回头路或相邻路径段之间发生错误跳转。

同时，系统计算机器人到路径投影点的横向误差：

```text
cross_track_error = 机器人当前位置到参考路径的距离
```

横向误差较大时只记录警告；超过```cross_track_abort```时取消当前目标并终止导航，避免机器人已经明显偏离参考路线却仍然继续推进路径进度。

#### 4.3.3 根据路径曲率计算前视距离

前视距离```lookahead```表示：

```text
从机器人当前路径进度开始，沿参考路径向前取多远
```

如果当前进度为```s = 2.40 m```，前视距离为```0.35 m```，则虚拟目标所在的路径位置为：

```text
target_s = 2.40 + 0.35 = 2.75 m
```

前视距离不是固定值，而是根据机器人前方路径的弯曲程度调整：

```text
直线段：曲率小，前视距离较大
弯道段：曲率大，前视距离较小
```

原因是：直线段可以提前看远一些；急弯如果看得太远，机器人可能直接切弯，偏离参考路径。

当前参数为：

```yaml
lookahead_min: 0.20
lookahead_max: 0.50
lookahead_curvature_gain: 0.45
```

算法先检查```progress_s```到```progress_s + lookahead_max```范围内的最大绝对曲率，再按照下面的关系计算前视距离：

```text
lookahead = lookahead_max
            / (1 + lookahead_curvature_gain * preview_curvature)
```

计算结果最后限制在```0.20 m```到```0.50 m```之间。例如：

```text
前方是直线：lookahead 接近 0.50 m
前方是普通弯道：lookahead 可能约为 0.30 m
前方是急弯：lookahead 不能小于 0.20 m
```

#### 4.3.4 生成并更新移动的虚拟目标

得到当前路径进度和前视距离后，在路径上计算虚拟目标的位置：

```text
target_s = progress_s + lookahead
```

然后根据```target_s```在相邻离散点之间插值，得到虚拟目标的：

```text
目标 x
目标 y
目标 yaw
```

这个虚拟目标不是整条路径的终点，而是一个位于机器人前方的“移动小目标”。机器人每前进一段距离，就重新计算一次：

```text
第一次：机器人 s=1.00，目标 s=1.40
第二次：机器人 s=1.20，目标 s=1.60
第三次：机器人 s=1.50，目标 s=1.80
```

所以整个过程表现为：

```text
机器人向前移动
        |
        v
重新计算机器人在路径上的 s
        |
        v
重新计算前视目标 target_s
        |
        v
发送新的前视目标
```

这就是“机器人往前走，导航目标也沿参考路径向前移动”。它避免了机器人在每个离散点处停车，从而比逐点发布固定目标更连续。

当前目标并不是每个控制周期都发送，而是在以下情况之一发生时更新：

- 新目标比上一个目标沿路径前进超过```goal_update_distance```；
- 距离上一次发送目标超过```goal_update_period```；
- 旧目标已经返回```SUCCEEDED```。

当前配置为：

```yaml
goal_update_distance: 0.12
goal_update_period: 0.8
```

#### 4.3.5 通过 MoveBaseGoal 执行虚拟目标

```navigation_stage.py```中的```NavigationStage```对标准的```move_base_msgs/MoveBaseAction```进行封装。它不接收完整的```nav_msgs/Path```，只接收任务服务器计算出的当前虚拟目标位姿。

每次发送时，逻辑是：

```text
虚拟目标 (x, y, yaw)
        |
        v
转换为 PoseStamped
        |
        v
封装为 MoveBaseGoal
        |
        v
发送到 /move_base
```

相邻的前视目标通过新的```send_goal```直接替换旧目标，不需要先显式取消再发送。这样可以利用Action的抢占机制连续更新目标，减少：

```text
取消目标 → 机器人停止 → 重新发送目标
```

所造成的停顿。

```move_base```收到当前前视目标后，仍然按照标准导航流程工作：

1. GlobalPlanner根据地图为当前目标计算可行的全局规划结果；
2. 局部规划器根据局部代价地图、激光数据和机器人运动约束选择速度；
3. 局部规划器发布```/cmd_vel```；
4. 机器人朝当前前视目标运动。

因此，拟合路径是机器人的平滑路线参考，```move_base```负责实际的路径规划、局部避障和速度控制。当前设计允许机器人因局部障碍暂时偏离拟合路径，但偏离不能超过横向误差阈值；若长期无法前进或偏离过大，则任务进入失败或重试流程。

#### 4.3.6 最终到达判断

中间的前视目标不是最终任务目标，因此不要求机器人在每个前视点完全停稳。中间过程主要检查：

```text
路径进度是否持续增加
横向误差是否在允许范围内
move_base 是否出现失败状态
```

当机器人距离拟合路径终点较近时，任务服务器停止继续生成移动前视目标，改为发送原始最终暂存点。只有最终目标的```move_base``` Action返回```SUCCEEDED```，任务才进入```ARRIVED_PICKUP_STAGING```。

当前还设置了：

- 单个目标超时时间：```60 s```；
- 最大重试次数：```1```；
- 完整路线超时时间：```240 s```；
- 路径进度长时间不增加时终止；
- 横向误差超过阈值时终止。

因此，完整导航链路可以概括为：

```text
AMCL / TF 提供机器人当前位置
        |
        v
将机器人位置投影到参考路径，得到 progress_s
        |
        v
根据前方曲率计算 lookahead
        |
        v
得到 target_s = progress_s + lookahead
        |
        v
在参考路径上插值得到移动虚拟目标
        |
        v
发送 MoveBaseGoal 到 /move_base
        |
        v
GlobalPlanner + DWAPlannerROS + 代价地图输出 /cmd_vel
        |
        v
机器人前进后重复上述过程
        |
        v
接近终点后发送精确最终目标并等待 SUCCEEDED
```

其中，```/sim_task/reference_path```主要用于发布和可视化完整参考路径；当前真正参与控制的是任务服务器内存中的拟合路径数据以及不断更新的```MoveBaseGoal```。

- 工作空间编译需要```catkin_make```及其构建工具。若系统尚未安装，可以补充：

  ```bash
  sudo apt install -y build-essential cmake python3-catkin-tools python3-rosdep
  ```

- 路径拟合脚本```src/gazebo_map/scripts/plot_fitted_navigation_path.py```不是 ROS 节点，依赖 Python 3 的以下第三方库：

  - ```numpy```：路线平滑、样条拟合和曲率计算；
  - ```Pillow```：绘制拟合路径示意图；
  - ```PyYAML```：读取和写入路线 YAML 配置。

  Ubuntu 环境可以直接安装对应系统包：

  ```bash
  sudo apt install -y python3-numpy python3-pil python3-yaml
  ```

  也可以使用 pip 安装当前用户环境中的同名包：

  ```bash
  python3 -m pip install --user numpy Pillow PyYAML
  ```

- 任务状态机和单元测试使用 Python 标准库```unittest```；通过 catkin 测试时还需要```python3-nose```：

  ```bash
  sudo apt install -y python3-nose
  ```

- 本工程自带```roboticsgroup_gazebo_plugins```源码包，因此不需要另外下载同名插件。它会在```catkin_make```时编译生成 Gazebo 机械臂关节相关插件。

- 如果只运行已经生成好的导航路线，不需要安装 SciPy；当前拟合程序使用 NumPy 自己实现正则化和自然三次样条计算。只有在修改拟合程序时，才需要额外注意 NumPy、Pillow 和 PyYAML 是否能够正常导入。

- 安装完成后，进入工作空间重新编译并加载环境：

  ```bash
  cd /home/ianichinose/gazebo_ws
  source /opt/ros/noetic/setup.bash
  catkin_make
  source devel/setup.bash
  ```
